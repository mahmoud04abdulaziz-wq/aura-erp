# AURA ERP - Polishing Phase Implementation Plan

This document outlines the final polishing phase for the AURA ERP system. The goal is to upgrade the system from a functional prototype to a professional-grade, automated web application. 

The work is divided into 9 Work Packages (WPs) across 4 Phases.

---

## Phase 1: Foundation & Data Integrity
### WP1: Pricing Strategy & Currency Standardization
*   **Objective:** Add selling prices to all finished goods.
*   **Tasks:**
    *   Add a `selling_price` column to the `item_master` table.
    *   Set the base currency for all storefront pricing, procurement, and financial reporting strictly to **JOD** (Jordanian Dinar).
    *   Calculate selling prices to ensure profitability relative to procurement costs.

### WP2: Database Cleanup
*   **Objective:** Resolve existing data inconsistencies.
*   **Tasks:**
    *   Identify and purge the 17 "orphan" sales orders (orders that exist in the header table but have no associated line items).
    *   Ensure foreign key constraints or application-level checks prevent empty orders from being created in the future.

---

## Phase 2: Production & Operations
### WP3: Smart Production Optimizer Engine
*   **Objective:** Automate production planning with an algorithmic optimizer.
*   **Tasks:**
    *   When an order is targeted (e.g., an order requires 200 Artificial Granite units), the system must suggest the best mix recipe to fulfill it.
    *   **Algorithm 1 (Fastest):** Finds the recipe that produces the highest yield per batch, minimizing the number of iterations to save time.
    *   **Algorithm 2 (Cheapest):** Finds the recipe that utilizes the lowest-cost raw materials per unit, even if it requires more iterations.
    *   Provide a toggle/switch on the UI for the production manager to choose between Fastest and Cheapest based on urgency.

### WP8: Kanban & Workflow Realignment
*   **Objective:** Enforce strict production constraints.
*   **Tasks:**
    *   Ensure that every single production batch generated by the optimizer is strictly linked to a specific Sales Order ID.
    *   Prevent "blind" production runs to eliminate raw material waste.
    *   Update the Kanban board to reflect these linked batches accurately as they move through Mixing -> Curing -> Finishing.

---

## Phase 3: Public-Facing Pipelines
### WP6: Site User Registration & Authentication
*   **Objective:** Allow public users to create accounts safely.
*   **Tasks:**
    *   Implement an OTP (One-Time Password) verification system for new site users.
    *   **Demo Mode Behavior:** When registering, the system should generate the OTP and display it directly on the screen (via a toast notification or alert) for easy testing and grading.
    *   **Production Mode Behavior:** The system should securely email the OTP to the user.
    *   *Note: Implement using standard PHP sessions and mail logic.*

### WP7: Public Careers & Hiring Pipeline
*   **Objective:** Create a realistic HR recruitment funnel.
*   **Tasks:**
    *   Build a public-facing `careers.php` page where external users can view job openings.
    *   Allow candidates to upload their CVs (PDF/Word).
    *   Create an HR dashboard where managers can review submitted CVs and click "Schedule Interview" to set up an in-person factory meeting. No external APIs are required.

---

## Phase 4: Analytics & Automation
### WP4: Production Lead Times
*   **Objective:** Track factory efficiency.
*   **Tasks:**
    *   Calculate the time difference between when an order enters "In Production" and when it is marked "Delivered".
    *   Display average lead times on the Management Dashboard.

### WP5: Economic Order Quantity (EOQ) Reports
*   **Objective:** Optimize raw material procurement.
*   **Tasks:**
    *   Implement a report that calculates the ideal reorder quantity for raw materials based on historical consumption rates and lead times, ensuring stock never runs out during peak production.

### WP9: Archiving Automation
*   **Objective:** Keep the active sales tables clean and fast.
*   **Tasks:**
    *   Create a CRON job or application-level trigger that automatically moves orders from the active `sales_orders` table to an `order_archive` table exactly 24 hours after their status is changed to "Delivered".
    *   Ensure archived orders are still visible in historical financial reports.
